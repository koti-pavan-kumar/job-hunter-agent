# Resume Creation Methodology

## Complete Guide for Pavan Kumar Koti's Professional Resumes

This document outlines the complete methodology for creating ATS-optimized, tailored resumes following Pavan's established rules and best practices.

---

## 1. CORE PHILOSOPHY - THE THREE RULES

### Rule 1: Tailor Every Resume
- **Never send the same resume to two different roles**
- Each resume is rebuilt from scratch around the specific JD language, keywords, and responsibilities
- The order of projects changes every time based on the JD

### Rule 2: Honest Framing Only
- Every skill claimed must be genuinely held
- If something is at conceptual/learning level, it is labeled '(fundamentals)' or '(learning)'
- **Never claim expertise that cannot be defended in an interview**

### Rule 3: ATS First, Human Second
- The resume must pass automated keyword screening before it reaches a human
- Every key term from the JD must appear naturally in the resume
- Use plain paragraph structure, no tables/columns/text boxes

---

## 2. NEW HARD RULES (Override Previous Methodology)

### Rule A: One Page Always, No Exceptions
- For a fresher/student resume, **one page is a hard rule, not a guideline**
- Standard font sizes:
  - Name: 44pt
  - Section headers: 22pt
  - Body/bullets: 19pt
  - Sublines/dates: 18pt
  - All Arial font
- **Do NOT shrink font sizes to force a one-page fit**
- When content overflows:
  1. Cut a project (down to 2, sometimes 3 if each is short)
  2. Tighten the objective to 3-4 sentences
  3. Cut to 2 bullets per project instead of 3
  4. Trim achievements to 3-4 lines
  5. Adjust margins/spacing only as a last resort
- The page must look genuinely FULL, not padded with excess white space
- **ALWAYS verify actual page count by rendering to PDF**

### Rule B: No 'Why [Company]' Section on Resume
- This section has been **REMOVED from resume structure entirely**
- 'Why [Company]' content belongs in the **COVER LETTER**, not the resume
- Cutting this section alone typically saves a third of a page

### Rule C: Cover Letters Are Always .docx Files
- **Never create cover letters in plain text format**
- Always use .docx format for cover letters
- This applies to every cover letter, no exceptions

### Rule D: AI-Assisted Development Must Always Be Disclosed
- If a project was built substantially using an AI coding tool (Codex, Claude Code, Cursor, etc.), this must be stated explicitly
- **Never claim full authorship of AI-generated code without disclosing the tool**
- Correct framing: 'built using AI-assisted development (tool name), reviewed and manually refined'
- This disclosure is not a weakness — for AI/ML-adjacent roles it can be a relevant skill

### Rule E: Verify Every Factual Claim Before Using It
- When a person states a skill or credential, ask for verifying detail before using it
- When a person provides a file, actually open and read it before building resume content
- When a person corrects a fact, treat it as final going forward

### Rule F: Legitimacy Screening
- Watch for ed-tech/bootcamp companies disguised as employers
- Check company website language for training/learning/skilling keywords
- Verify actual business model before building a resume
- Red flags: paid courses, "certificate of internship", excessive openings

### Rule G: Zero Exposure = Do Not Bridge
- The bridging system (fundamentals/learning/concepts tags) is for **PARTIAL exposure only**
- If there is ZERO exposure to a hard, specifically-named requirement, **do not bridge it**
- Either flag as a reason to reconsider, or disclose as a plain, direct gap
- Rule of thumb: if the gap is in a JD's 'required' section with zero adjacent exposure, tell the person plainly before building anything

### Rule H: Check the Pattern for Off-Domain Applications
- When applying to multiple genuinely unrelated fields within one session, surface this directly
- First off-domain role: flag clearly, explain the mismatch honestly
- If a THIRD or later unrelated field appears, name the pattern explicitly

### Rule I: Numeric-Only Form Fields
- When an application form specifies 'numbers only, no decimals, no characters', answer in exactly that format
- Round sensibly and explain the reasoning, but do not add units, symbols, or explanatory text inside the field value itself

## 4. ATS OPTIMIZATION RULES

### Keyword Strategy
- Extract **EXACT phrases from JD** — not synonyms
- If JD says 'Exploratory Data Analysis', write 'Exploratory Data Analysis' not 'EDA exploration'
- Put highest-priority keywords in:
  - Objective (first paragraph)
  - Skills section
  - First bullet of most relevant project
  - Why [Company] section (in cover letter)

### Formatting Rules
- **Avoid tables, columns, headers/footers, text boxes** — ATS systems cannot parse these
- Use plain paragraph structure only
- File format: Always save as PDF for submission
- Font: Arial throughout
- Colors:
  - Blue: #1a56db (for headers and section lines)
  - Black: #0d0d0d (body text)
  - Gray: #444444 (sublines/dates)
  - Light Gray: #666666

### Section Header Formatting
- All caps with blue bottom border line
- Examples: TECHNICAL SKILLS, PROJECTS, EXPERIENCE

### Bullet Point Rules
- Start every bullet with a strong action verb: Built, Designed, Implemented, Engineered, Developed, Achieved, Processed, Deployed, Collaborated
- Include at least one quantified metric per project
- JD language mirroring: If JD says 'ground truth datasets', write 'ground truth datasets'
- Length: 1.5-2 lines per bullet

## 8. ROLES TO AVOID — RED FLAGS

### Role Types to Skip
- **Operations roles** (Goldman Sachs Operations, Genpact Operations): No overlap with skills
- **Cybersecurity/SOC roles** (KPMG SOC Analyst): SIEM, threat hunting, malware analysis — zero overlap
- **Pure Finance roles** (J.P. Morgan Commodities): Derivatives lifecycle, KDB database — completely different domain
- **Data Entry/Annotation roles**: Repetitive manual work, no technical growth
- **Roles requiring ETL tools** (Informatica, Talend, Airflow): Only if no exposure — don't bridge this

### Company Legitimacy Red Flags
- .cc, .tk, .xyz domain emails — not legitimate business emails
- 'Refer & Win' banners prominently featured — MLM-style operation
- Vague JD with no specific responsibilities — copy-paste generic posting
- Asking for payment at any stage — immediate red flag, report to platform
- No LinkedIn company page or employees listed — unverifiable company
- Ed-tech/bootcamp companies disguised as employers

## 9. COVER LETTER METHODOLOGY

### Structure (5 Paragraphs)
1. **Para 1 — Hook**: One powerful opening statement about what makes Pavan relevant. NOT 'I am writing to apply...' but something specific and confident.
2. **Para 2 — Primary proof point**: The most relevant project mapped to their exact JD language. Quote numbers.
3. **Para 3 — Secondary proof**: Second project OR current internship relevance.
4. **Para 4 — Credibility signals**: Amazon MLSS, Flipkart GRiD, current Bluestock internship.
5. **Para 5 — Why THIS company**: 2-3 sentences specific to their mission/product. Never generic.
6. **Close — Availability + call to action**

### Cover Letter Rules
- **Never start with 'I am writing to apply'** — too generic
- Always include specific metrics (99% reliability, 95.8% Recall, 270+ tests, 87,000+ rows)
- Mirror the company's own language back to them — use their JD words
- **Always create in .docx format** (Rule C)

### Company-Specific Hooks
- For Optum: Lead with healthcare AI mission alignment
- For Salesforce: Lead with 'contribute to live projects not sit in training rooms'
- For HARMAN: Lead with 'I build production-grade agentic AI systems — not demos'
- For Enverus: Lead with 'I build real-world GenAI solutions'
